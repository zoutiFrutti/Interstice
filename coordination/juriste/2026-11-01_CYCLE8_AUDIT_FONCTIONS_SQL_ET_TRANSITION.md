## Faits SQL contrôlés directement
Les cinq fonctions `public.is_moderator`, `moderate_proposal`, `moderate_resource`, `review_wiki_article` et `submit_wiki_article` sont `SECURITY DEFINER`, exécutables par `authenticated`, non par `anon` selon les privilèges SQL vérifiés. **Nouvelle lecture complète via `pg_get_functiondef`** : `is_moderator` vérifie `auth.uid()` dans `moderator_accounts`. Les trois RPC de modération appellent `is_moderator()` avant leurs modifications ; `moderate_proposal` et `moderate_resource` limitent les états possibles, `review_wiki_article` exige un motif et enregistre la revue. **Correction des alertes antérieures :** EXECUTE pour le rôle `authenticated` ne signifie pas que tout compte connecté peut modérer ; des gardes de rôle sont présentes dans le code. Leur efficacité avec des comptes tests et les politiques de la table `moderator_accounts` reste à éprouver. Ne pas déclarer une faille de modération démontrée.
`submit_wiki_article` exige `auth.uid()`, des champs contrôlés, deux confirmations booléennes et un maximum de trois envois par 24 h ; **ne contient pas de drapeau de suspension globale**. Compte connecté valide + entrées acceptées pourraient donc encore déclencher une insertion : si l'objectif est de suspendre toutes les soumissions, ce chemin reste P0 ouvert. Pas de requête d'écriture ni de reproduction dynamique faite.
Edge Functions : audit du code sur PR #67 `coordination/juriste/2026-11-01_CYCLE8_AUDIT_CODE_DEPLOYE_ENDPOINTS.md` : `submit-proposal` et `submit-resource` n'ont que des garde-fous Origin/quotas et restent actives ; `github-wiki-ingest` dispose d'une authentification OIDC GitHub et ne doit pas être neutralisée aveuglément.
